## 2. 开始下一阶段前应处理的问题

### 2.1 OSI 的训练/测试精度不一致

`data_loader.reconstruct_osi` 对已有训练 osi 原样保留，对测试则使用组件重建且不舍入。训练 osi 保留四位小数；`frac_zero_72h` 又使用严格 `== 0`。

- 训练观测窗口：存储 osi 的零比例 47.68%；组件重建不舍入为 26.94%；重建后 round(4) 恢复为 47.68%。
- 测试观测窗口：当前重建为 28.33%；round(4) 后为 50.84%。
- 在 239 个训练县中，231 个县采用两种精度会得到不同的零比例特征，单县最大差异约 63.9 个百分点。

建议统一训练与测试的观测特征计算口径：优先从相同存储组件重建并按训练标签精度舍入，再生成包括零比例在内的全部摘要。标签仍使用官方存储目标，不能自行修改。至少要做一次“将验证县伪装成测试格式”的验证：去掉其 osi 和后 72 小时以外的停电信息，再走同一输入管线。

这属于真实的输入分布偏移，不代表修复后测试分数必然提高；测试标签不可见。修正应另存版本，保留旧基线。

### 2.2 外部 n_utilities 合并了不同州的同名县

`data/external/scripts/build_county_features.py` 第 93 行仅按 `County` 统计 Utility Number，随后仅以县名取值。应使用 `(State, County)` 并映射到 FIPS。

实查 EIA：Adams 在 IN/OH/PA 的电力公司数分别为 4/4/2；目前三州同名县合并为 10，缓存中 Indiana Adams 即为 10。应修正统计和连接并另存特征版本。不要因为当前特征重要性较低就假定该错误没有影响。

### 2.3 工程可复现仍依赖现成缓存

- 当前 config 默认 v1.5.3，不是本次指定基线。
- 当前 features.py 不包含完整 v1.5.2 外部拼接；协议也明确禁止用它重建现有缓存。`join_external.py` 未在当前文件树中发现。
- 原训练代码只在内存保留 OOF，未保存逐折模型和原始 OOF。目录中四个模型是全量重训模型，不能直接拿其训练集预测当折外预测。
- Git 检出后的模型文本为 CRLF，而索引中为 LF；直接加载触发 tree format error。在内存统一为 LF 后正常加载并重现提交。应固定这些模型文本的换行或加载规范，不应更改树参数。

建议冻结 feature names、原始数据/缓存摘要、依赖版本、折清单、模型参数、逐折树数、raw/postprocessed OOF 和模型文件；补齐从原始数据到 141 列特征及预测的明确入口。此次复核不修改既有代码、特征或提交。

### 2.4 两个实验解释需要调整

保存模型均为 `objective=huber, alpha=0.9`。LightGBM 的 Huber 实现以 alpha 直接作为残差转折点。本次训练目标最大值按 horizon 为 0.5447/0.4704/0.3277/0.3277，当前尺度下训练基本处于平方误差区域，因此不能把效果解释为已验证的异常值鲁棒性。没有必要因此否定基线；若要研究鲁棒损失，应显式调整阈值并另做受控对照。

依据：[LightGBM Huber 源码](https://github.com/microsoft/LightGBM/blob/v4.6.0/src/objective/regression_objective.hpp)、[参数说明](https://lightgbm.readthedocs.io/en/latest/Parameters.html)。

零比例接近目标零比例不等于回归校准正确。实测将小于 0.001 的预测置零，在全部四个 horizon 上改善 MAE、轻微损害 RMSE。例如 1h RMSE 从 0.01222849 变为 0.01223223，MAE 从 0.00370471 变为 0.00365437。48h 也呈相同权衡。

官方本地 PDF 未给出最终计分公式，仅说另行发布。因此暂时同时报告 RMSE/MAE，不应预设短 horizon 权重更大。不同 horizon 覆盖的目标时段不同，不能把较小的 48h RMSE 解释为长期预测更容易。

## 3. GRU 残差建模的依据与边界

现有 LightGBM 将前 72 小时历史压缩成摘要。不同县可能有相同均值、峰值与末尾状态，却有不同的恢复过程、风暴响应滞后或恶化轨迹。GRU 有机会提取这些未被摘要保留的顺序信息。

本次 OOF 残差的同县一小时滞后相关系数为 0.930/0.919/0.898/0.893；先减去各县平均残差后仍为 0.917/0.904/0.875/0.864。这说明残差有连续结构，但不能据此推断该结构一定可由合法输入预测。真实历史残差在测试预测期并不存在，不能作为 GRU 输入。

仅 239 个县、一个连续双风暴窗口，144 小时行高度相关；34,416 行不能当作同等数量的独立序列。1h/48h 中，误差最大的五个县分别占总平方误差约 51.5%/61.4%。因此收益应报告逐折、逐县和风暴阶段，使用按县整条轨迹抽样的配对 bootstrap；不能逐行 bootstrap，也不能因少数极端县难预测而直接删除它们。

## 4. 推荐的第一版模型与验证协议

残差定义建议为 `r(c,t,h) = y(c,t,h) - b_raw(c,t,h)`，输出为 `postprocess(b_raw + alpha_h * GRU(...))`。保存 raw 与后处理后的基线预测；若选择以后处理基线为残差参考，也必须在训练和测试中一致，不要两种定义混用。残差输出允许正负，不使用 ReLU/softplus 强制为正。物理范围裁剪和零阈值放到合成预测之后。

第一版建议：72h 观测历史编码器 + 从观测截止后到目标时刻的天气序列解码器 + 少量县级静态特征与目标时间位置。可将基线预测作为额外已知输入。GRU 先用 1 层、hidden 32 或 64、权重衰减和小型输出头，末层可零初始化；不必直接采用 Plan.md 的两层 hidden 128。隐藏状态按县重置，归一化统计只在相应训练县拟合；不要仅做县内标准化而丢掉绝对停电严重程度。

验证必须覆盖整个两阶段系统：

1. 外层继续使用 balanced_v1 五折，每次完整留出一组县。
2. 仅在外层训练县内做内层按县交叉拟合，为这些县生成 LightGBM 折外预测与残差标签；内层模型的树数选择也不能使用外层验证标签。
3. GRU 在这些内层残差上训练，早停、残差缩放、alpha、阈值等均只在外层训练数据内部选择。
4. 在外层训练县上重训基模型，预测外层验证县，再用 GRU 修正。该验证县标签只能用于最后评分。
5. 合并外层预测评估完整系统；最终训练时，在全体训练县内部交叉拟合得到残差标签，并使最终基线预测的训练方式尽量匹配验证协议。

特别注意：全数据先做一次五折 OOF，再直接用同一五折评估 GRU，并不严格隔离外层验证。用于 GRU 训练的“其他四折的 OOF”可能来自看过当前外层验证县标签的 LightGBM，形成间接泄漏。现有 OOF 可用于诊断；正式效果评估需要上述嵌套程序。

折外训练预测是标准 stacking 的基本要求；参见 [scikit-learn StackingRegressor](https://scikit-learn.org/stable/modules/generated/sklearn.ensemble.StackingRegressor.html)。上述嵌套安排是在本项目按县留出的评估要求下对这一原则的应用。

GRU 不读取预测期真实停电、真实 OSI 或真实残差；本地 OSI_Methodology.pdf 也明确禁止填补测试预测期停电 NaN。建议第一版直接输出修正量，避免将预测值写回原始停电列。官方邮件已要求使用存储的 N_t/R_t，不能根据文档净变化公式自行重算它们。

## 5. 一个比加模型更便宜的结构对照

本赛所有预测原点共享同一份前 72 小时停电历史，且全窗口气象都可用。因此 `y(c,t,h)=OSI(c,t+h)`，不同 `(t,h)` 可能对应同一个目标小时，区别主要来自目前四个模型及特征表示，而非新增停电观测。

可以学习同一条未来 OSI 轨迹，再按四个 horizon 映射；或者用共享 GRU 状态和四个残差头，并检验目标时刻一致性。不应把文档中“同一原点 1h 与 48h 目标相关性很低”理解为这些输出不可共享时序表示。

额外诊断：将现有 OOF 的原始预测按 `(县, 目标小时)` 对齐，对可用模型取无权平均，最后只做一次原后处理。该对照没有拟合权重，也没有使用目标值生成预测：

|---|---:|---:|---:|---:|---:|
| 1h | 0.01223223 | 0.01200367 | -1.9% | 0.00365437 | 0.00359151 |
| 6h | 0.01067706 | 0.01057935 | -0.9% | 0.00353758 | 0.00337717 |

这是原开发 CV 上的新对照，不是已确认的测试集收益，也不是推荐立即全量替换。它说明结构共享值得与 GRU 同时比较。

建议实验顺序：冻结旧基线 → 修正输入口径与连接、形成新基线 → 保存 OOF 并诊断 → 简单残差回归/目标时刻对齐对照 → 小 GRU 残差 → GRU 直接预测再与 LightGBM 融合作对照。最终比较以同一嵌套验证下的完整预测系统为准。
