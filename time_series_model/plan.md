我建议第一版采用一个小型的“因果双段 GRU + LightGBM 残差修正”模型。先直接修正 v1.5.6 的四个 OSI 预测，不在第一版同时做 P/N/D/R 分量残差。

整体形式是：

\[
\hat y_{c,t,h}
=
\operatorname{postprocess}
\left(
b_{c,t,h}
+
\alpha_h\Delta_{c,t,h}
\right)
\]

其中：

- \(b_{c,t,h}\)：v1.5.6 LightGBM 的原始预测；
- \(\Delta_{c,t,h}\)：GRU 预测的正负残差；
- \(\alpha_h\)：每个 horizon 独立的残差缩放系数；
- \(s=t+h\)：实际目标时刻；
- 裁剪和置零后处理只在 LightGBM 与 GRU 相加之后执行。

## 1. 为什么第一版选择 GRU

目前适合的候选包括 GRU、LSTM、TCN 和 Transformer/TFT，我建议从 GRU 开始。

| 模型 | 当前适合度 | 原因 |
|---|---|---|
| 小型 GRU | **最高** | 参数少，适合239个县的小样本；能编码状态持续、风暴滞后和恢复过程 |
| TCN | 次选 | 训练稳定、容易并行，可作为GRU之后的时序对照 |
| LSTM | 较低 | 比GRU参数更多，当前数据量下未必有额外收益 |
| Transformer/TFT | 暂不建议 | 数据只有一个双风暴事件，独立样本实际上接近239条县级序列，过拟合风险高 |

虽然特征表有34,416行，但这些行来自239个县的高度重叠时间窗口，不能当作34,416个独立样本。当前残差的一小时滞后相关系数约为0.89～0.93，说明残差确实有很强的连续结构；但这种相关性可能包含县级系统偏差和时间平滑，只有严格验证后才能证明 GRU 能从合法输入预测它。已有分析见 [Baseline_Review_2026-09-08.md](C:/Users/yongyi.xie/INFORMS_DATA_MINING/fundamentals/1.5.5特征检查与未来气象特征/Baseline_Review_2026-09-08.md:72)。

## 2. 第一版模型结构

不建议简单地把每一行整理成一个独立的72小时样本。更合理的训练单位是“一个县的一整条时间序列”。

### 2.1 第一段：72小时观测历史编码器

输入为 hour 0～71 的真实观测序列。

停电变量建议使用：

- `P_t`
- `N_t`
- `D_t`
- `R_t`

可以不额外输入 OSI，因为它是四个分量的确定性线性组合。不过可将 `last_osi` 作为跳跃连接直接送到输出头，帮助模型保留最后状态。

同期天气建议先使用一组精简变量：

- `gust`
- `wind_speed`
- 风向的 `sin/cos`
- `t2m`
- `tp`
- `sp`
- `r2`
- `csnow`
- `soil_moist`

通过一层 GRU 将72小时压缩为县级初始状态 \(z_c\)。这部分学习：

- 停电是正在上升、平台还是恢复；
- 天气冲击与停电变化之间的滞后；
- 最后一个小时相同、但此前轨迹不同的县级状态。

### 2.2 第二段：未来天气编码器

从最后停电观测之后，即 hour 72 开始，用另一个单向 GRU 依次读取未来天气：

\[
W_{c,72},W_{c,73},\ldots,W_{c,215}
\]

这个 GRU 的初始隐状态由第一段的 \(z_c\) 生成。它在每个未来小时 \(s\) 产生一个天气影响状态 \(u_{c,s}\)。

这样每个县的未来144小时天气只需要编码一次。对某个提交位置 \((t,h)\)，直接取 \(s=t+h\) 对应的状态 \(u_{c,s}\)。

第一版建议只读取目标时刻之前的天气，即 `[72,s]`。虽然比赛允许看到目标之后的天气，但先采用这种单向、目标截止设计，物理含义更清楚，也能减少模型通过风暴整体形状记忆时间位置。

### 2.3 静态与基线输入

在输出头前拼接：

- 历史编码状态 \(z_c\)；
- 目标时刻天气状态 \(u_{c,s}\)；
- v1.5.6 LightGBM 原始预测 \(b_{c,t,h}\)；
- `last_P_t/N_t/D_t/R_t/last_osi`；
- `s_minus_o = s-71`；
- 当前 horizon 的类别或嵌入；
- 少量县级静态特征。

静态特征建议控制在大约8～12列：

- `log_customers`
- `pop_density`
- `pct_forest`
- `pct_wetland`
- `tree_canopy_pct`
- `tree_canopy_std`
- `n_utilities`
- `customers_per_utility`
- 城乡等级的合理编码

不输入 `fipsCode` 和 `stateAbbr`，也不使用县ID embedding。否则模型很容易记住训练县，而无法泛化到测试县。

### 2.4 共享编码器、四个残差头

建议两个 GRU 编码器由四个 horizon 共享，最后使用四个很小的输出头：

```text
72h停电+天气 ── 历史GRU ── z_c
                            │
未来逐小时天气 ── 未来GRU ── u_c,s
                            │
     静态特征 + LightGBM预测 + 时间位置
                            │
             1h / 6h / 24h / 48h 残差头
```

每个输出头只需要一到两层小型全连接层。共享编码器可以让四个 horizon 共同学习风暴传播和恢复过程，独立输出头则保留不同 horizon 的误差特征。

第一版不建议为四个 horizon 分别训练四套完整 GRU，因为那会把仅有的239个县进一步拆散，并显著增加过拟合风险。

## 3. 推荐的初始规模

第一版应刻意保持小型：

- 历史 GRU：1层，hidden size 32；
- 未来天气 GRU：1层，hidden size 32；
- 输出头：32或64维中间层；
- 显式 dropout：0.1或0.2；
- AdamW；
- weight decay：从 `1e-4` 或 `1e-3` 开始；
- gradient clipping：1.0；
- 最终残差层零初始化。

单层 PyTorch GRU 自带的层间 dropout 实际不会生效，因此如果只用一层，应在输入或输出位置显式放置 dropout。

最终层零初始化的意义是：训练刚开始时 GRU 修正量为0，整个系统等于 v1.5.6 基线。之后只有找到稳定残差信号时，模型才逐渐偏离基线。

初次调参只比较少量组合即可：

- hidden：32、64；
- dropout：0.1、0.2；
- loss：Huber、MSE；
- residual shrinkage \(\alpha_h\)：1.0或由内层验证选择。

不建议第一轮就使用两层128维 GRU。原 [Plan.md](C:/Users/yongyi.xie/INFORMS_DATA_MINING/Plan.md:153) 中的两层 hidden=128 对当前有效样本量偏大。

## 4. 残差标签怎么构造

必须使用 LightGBM 的折外预测：

\[
r_{c,t,h}=y_{c,t,h}-b^{OOF}_{c,t,h}
\]

这里建议使用后处理前的 LightGBM 原始预测 `b_raw`。原因是阈值置零是离散操作，会让残差分布突然跳变，不利于 GRU 学习连续修正。

训练时可以：

1. 按 horizon 计算训练县上的残差标准差 \(\sigma_h\)；
2. 让 GRU 预测标准化残差 \(r/\sigma_h\)；
3. 输出时再乘回 \(\sigma_h\)。

这样 t+1h 的残差尺度不会压倒 t+48h，四个 head 可以按等权平均损失训练。由于官方最终计分公式尚未公布，不建议预设“短 horizon 权重更高”。

GRU 的残差输出允许正负，不能使用 ReLU 或 softplus。最终只在合成预测上做：

1. 加回 LightGBM；
2. 裁剪到物理范围；
3. 根据评分指标决定是否执行 `<0.001 → 0`。

当前置零策略改善 MAE、轻微损害 RMSE，所以需要同时保存：

- 原始合成预测；
- 仅裁剪预测；
- 裁剪加置零预测。

## 5. 最关键的防泄漏设计

不能直接拿现有五折 OOF 残差训练 GRU，再用同一套五折 OOF 行报告 GRU 成绩。这样会产生间接泄漏。

原因是：某个 GRU 训练县的 LightGBM OOF 残差，可能由一棵训练时看过当前 GRU 验证县标签的 LightGBM 生成。

正式验证需要嵌套按县交叉验证：

### 外层五折

继续使用当前 `balanced_v1`，每次完整留出一组县，作为整个“LightGBM + GRU”系统的最终验证县。

### 外层训练县内部

在剩余县中再按县分折：

1. 生成内层 LightGBM 折外预测；
2. 用这些预测构建 GRU 残差标签；
3. 在外层训练县内部选择 hidden size、epoch、\(\alpha_h\) 和后处理；
4. 不能查看外层验证县标签。

### 外层验证

1. 用全部外层训练县重训 v1.5.6 LightGBM；
2. 预测外层验证县，得到 `b_raw`；
3. GRU 根据外层验证县的合法输入序列预测残差；
4. 合成并评分。

最后合并五个外层验证折，才得到可与 v1.5.6 公平比较的池化 OOF 指标。详细原则已写在 [Baseline_Review_2026-09-08.md](C:/Users/yongyi.xie/INFORMS_DATA_MINING/fundamentals/1.5.5特征检查与未来气象特征/Baseline_Review_2026-09-08.md:82)。

现有 v1.5.6 OOF 可以用于开发、检查张量形状和观察训练是否收敛，但不能作为最终效果证据。

## 6. 输入归一化

所有归一化参数只能在对应折的训练县上拟合。

建议：

- 天气连续变量：全局标准化；
- `tp`、`csnow` 等大量为零且右偏的变量：先 `log1p`，再标准化；
- P/N/D/R：保留绝对量级后做全局标准化；
- 静态连续特征：标准化或稳健标准化；
- 城乡等级：one-hot 或小型有序编码；
- 缺失值：数值填充和缺失标志同时保留。

不建议只做县内 z-score。县内标准化会消除“这个县的停电比例本身特别高”“这个县的阵风绝对强度特别大”等重要信息。

## 7. 第一版需要的对照实验

为了证明收益确实来自“时序”，至少保留下面四个对照：

| 对照 | 目的 |
|---|---|
| v1.5.6 LightGBM | 原始基线，GRU修正量恒为0 |
| 目标时刻对齐平均 | 检查简单利用四个horizon一致性可以获得多少收益 |
| 非时序 MLP 残差模型 | 输入静态特征、LightGBM预测和普通摘要，不使用GRU |
| GRU 残差模型 | 完整时序方案 |

“目标时刻对齐平均”尤其重要。已有诊断中，它没有训练新参数，就让1h、6h、24h RMSE分别改善约1.9%、0.9%、2.2%，但48h退化1.1%。GRU 至少应与这个廉价方法比较，而不只是与原始 LightGBM 比较。

MLP 对照可以回答一个关键问题：

- 如果 MLP 和 GRU 改善相近，收益主要来自基线预测、静态特征或额外参数；
- 如果 GRU 明显更好，才说明天气和停电的先后顺序确实贡献了信息。

后续还可以做“打乱时间顺序”的负对照，但第一轮不是必需。

## 8. 评价标准

每个外层折和每个 horizon 都需要报告：

- 池化 OOF RMSE；
- 池化 OOF MAE；
- 相对 v1.5.6 的变化；
- 每折结果；
- 每县 RMSE/MAE；
- 最大误差县的贡献；
- 不同风暴阶段的误差；
- 预测零比例；
- 修正前后的残差自相关；
- 同一目标时刻由不同 horizon 得到的预测差异。

此外，应按“县的整条轨迹”做 paired bootstrap。不能逐行 bootstrap，因为同一个县相邻小时高度相关。

我建议把第一版的通过标准设为：

- 相同外层折下，组合模型在多数折和多数 horizon 上方向一致；
- 相对于 v1.5.6，平均标准化 RMSE 有稳定改善；
- 改善不能只来自一两个极端县；
- 至少优于非时序 MLP，或者明显改善目标时刻一致性；
- 三个随机种子的结论基本一致。

如果只出现“t+48h MAE 改善，但 RMSE和其他 horizon 退化”，更适合作为融合候选，不应直接替换基线。

## 9. 推荐的实验顺序

第一阶段只完成最小闭环：

1. 冻结 v1.5.6 原始预测、后处理预测和折分配。
2. 按县构造72小时观测序列与144小时未来天气序列。
3. 完成嵌套 CV 的 LightGBM 残差生成。
4. 训练单层 hidden=32 的 GRU 残差模型。
5. 与 v1.5.6、目标时刻对齐平均、非时序 MLP 比较。
6. 再测试 hidden=64、dropout 和损失函数。
7. 最后做三随机种子和按县 bootstrap。

第二阶段才扩展模型：

- 比较直接 GRU 与残差 GRU；
- 比较 GRU 和小型 TCN；
- 加入同一目标时刻的一致性约束；
- 将基线换成“v1.5.6 特征 + P/N/D/R 分量 LightGBM”；
- 再考虑分量残差或多任务输出。

第一版不建议同时加入 F1/F2/F3、不建议预测16个分量残差，也不建议直接上 TFT。否则一旦结果变化，很难区分收益究竟来自时序结构、特征变化、目标变化还是验证方式。

最终，我建议把第一版定义为：

> **v1.5.6 直接 OSI LightGBM + 共享小型双段 GRU + 四个 horizon 残差头，使用按县嵌套交叉验证。**

它既保留当前最可靠的树模型基线，也让 GRU 专门学习历史轨迹、天气顺序、滞后和恢复过程。这个方案复杂度足够低，失败时也容易判断失败发生在哪一层。
